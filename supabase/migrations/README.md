# migrations — سجل تغييرات قاعدة البيانات

الملفات هنا هي **مرآة لتاريخ الـ migrations المسجّل فعليًا في قاعدة Supabase**
(`supabase_migrations.schema_migrations`)، مُعاد بناؤها بايت‑ببايت من القاعدة.
كل ملف باسم `<version>_<name>.sql` ونفس الإصدار المسجّل في القاعدة، فالريبو
والقاعدة متطابقان في التاريخ.

| `20260920144533_rls_drop_redundant_duplicate_policies` | حذف سياستين مكرّرتين بالكامل (tasks، deals) — لا يغيّر الصلاحيات. |

## ⚠️ تنبيه مهم: الأساس (baseline) ناقص

تتبّع الـ migrations بدأ في **2026‑09‑20** فقط. السكيمة الأساسية — الجداول
(`leads`, `tasks`, `deals`, `profiles`, `roles`, `stages`, `branches`, …)،
الدوال (`archive_lead`, `unarchive_lead`, `check_duplicate_phone`,
`is_manager_safe`, `current_role_code`, …)، سياسات RLS الأصلية، والتعريف
الأول للـ view — كلها أُنشئت **قبل** بدء التتبّع، فهي **ليست** في أي ملف هنا.

يعني: تشغيل الملفات الحالية على قاعدة فارغة **لن يبني النظام من الصفر** —
لأنها تعدّل جداول/view يُفترض وجودها مسبقًا.

## لإكمال الأساس (يُنفَّذ مرة واحدة، محليًا)

استخدم Supabase CLI لسحب لقطة كاملة للسكيمة الحالية كأساس:

```bash
# ثبّت الـ CLI إن لم يكن موجودًا: https://supabase.com/docs/guides/cli
supabase link --project-ref svuoddaundjfnssvqnpv
supabase db pull            # يولّد ملف baseline بالسكيمة الكاملة الحالية
```

`db pull` سيصنع ملف migration يمثّل الحالة الكاملة. بعده يصبح الريبو قادرًا على
إعادة بناء القاعدة من الصفر.

## سير العمل بعد ذلك

- أي تغيير جديد في القاعدة: اكتبه كملف `.sql` جديد هنا (أو `supabase migration new <name>`)،
  وطبّقه بـ `supabase db push` — بدل تعديل القاعدة يدويًا من اللوحة.
- كده كل تغييرات السكيمة تبقى مُراجَعة في git ومتتبَّعة زي باقي الكود.
